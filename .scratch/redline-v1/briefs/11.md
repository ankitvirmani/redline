## The constraint that shapes everything

**The app must start, and must analyse a pasted document, with both Supabase
variables absent.** This is not a nice-to-have. The reader is deciding in the minutes
before they accept and will not stop to create an account, so a signup wall in front of
the paste box would cost the product its own use case.

That means:

- Nothing on the analysis path imports a Supabase client at module load in a way that
  throws when the variables are missing.
- A signed-out reader can paste, analyse, and read the full result: the summary, the
  completeness reading, every flag with its consequence, its external context, its exit
  and its source sentence, and the question box. All of it. Test this.
- With the variables absent, the account-gated surfaces say so in product copy rather
  than crashing, showing a blank page, or throwing into a console. That copy is a
  designed state: the owner will be running this app before they create the project, so
  it is the state they will see first.
- Only the library and red lines require an account. Nothing else.

Write a test that proves the analysis path works with both variables unset. Delete them
from the environment inside the test and run a full paste-to-result pass through the
stub. This is the criterion most likely to rot, because every later change that touches

## What to build

**1. Sign in and sign out.** Supabase auth. Which method is your decision and you
should justify it: a magic link needs no password handling and no password reset flow,
which is less to get wrong for a product holding contracts, and it needs email delivery
the owner has not configured. A password flow works the moment the project exists but
adds reset, strength and breach concerns. Pick one, say why, and write the migration and
configuration notes the owner needs to make your choice work.

**2. The library.** An analysed document is saved to a library belonging to that
reader. The library lists past documents and each can be reopened with its analysis.

**Only extracted text is stored. The uploaded file never is.** `CLAUDE.md` is
explicit. No file bytes, no base64, no blob, no storage bucket, no file name if you can
avoid needing one, and nothing in a Supabase Storage bucket at all.

Decide whether the analysis itself is stored alongside the text or recomputed on
reopen, and justify it. Storing it means the reader sees what they were shown rather
than a new analysis from a changed model, which matters for a product whose promise is
that the reader can check what they were told; recomputing means less data at rest and
no stale result. There is a real argument both ways and the owner will want to see
yours.

**3. A reader's documents are visible only to them.** Row-level security, written as
policy in the migration, not enforced only in application code. No sharing between
readers exists in v1 and none may be possible. Write the policies so that a select, an
insert, an update and a delete each require the row's owner to be the requesting reader,
and comment each one.

## The screen

The rail is the navigation, per `DESIGN.md`. It carries the mark, the library and the
reader's red lines. Follow the rail's existing composition: the 2.25rem ink mark square
with the white R at 900, the wordmark at 800 and 0.11em, the label register for section
labels, hairline-ruled list rows each with the 0.5rem by 0.1875rem ink marker that is the
bar motif at its smallest. At 860px the rail becomes a static top band with a 2px ink
bottom border and stays fully visible; there is no hamburger and no drawer in this
system.

An empty library is a designed state. It is not an error and not a blank panel. A
reader arrives at it having analysed nothing, so it says what the library is for.

Sign-in is a form in the Operate register: white field, 2px ink keyline, zero radius,
visible label above, global focus ring, cyan primary button with black uppercase label.
`DESIGN.md` records that error and disabled states are not in the build and must not be
invented casually, so whatever you design for a failed sign-in stays in world: an ink
bar in front of the line, as refusals get, rather than red text and a warning triangle.

Operate register throughout: motion 150 to 250ms and state only, no display type above
2.875rem, no scattered fragments, no overprint bar. WCAG 2.2 AA: the rail is real
navigation with a real accessible name, the library list is a list, and the sign-in
form's errors are associated with their fields.
