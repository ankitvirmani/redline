## The dependency question is already answered

The ticket says to stop and ask before adding a PDF parsing dependency. The owner is
not present for this run and the decision was made for you: **use `pdfjs-dist`**,
Mozilla's PDF.js. It is on the approved list in the standing brief. The reasoning is
recorded in `BUILD-REPORT.md` and comes down to the property that matters here, which
is that it exposes per-item text without normalising it, runs in the browser, and is
the parser Chrome's own viewer is built on. Do not add any other package. Do not add
a worker-loading helper library; wire the worker yourself.

## What to build

A reader uploads a PDF offer letter instead of selecting and copying it by hand. The
PDF is parsed in the browser and only the extracted text moves on. A PDF with no text
layer, and a scanned or photographed PDF, are refused with the reason shown in plain
language rather than analysed as empty.

It goes behind the extraction seam ticket 02 built, at `src/extraction/pdf.ts`. The
seam's public surface stays the same shape: nothing downstream should learn anything
new except the `sourceKind` field's value.

## The four hard parts

**1. Parsing happens in the browser and the file never leaves it.** No upload, no
`FormData` to a route handler, no temporary file, no server write, no logging of file
bytes or of the file name into anything that persists. The file is read in the browser,
parsed in the browser, and only the extracted text crosses to the server when analysis
runs. `pdfjs-dist` needs a worker; load it as a static asset from `public/` or through
Next's bundler, and make sure the build still passes. This is the part most likely to
fight you, so budget for it.

**2. Character fidelity through a PDF parser.** A text-layer PDF must yield text
character-identical to its text layer. PDF.js returns text in items with positional
data and no notion of lines or paragraphs, so assembling them into text is your
decision and it is a real one. You must decide when two items are the same line and
when a line break belongs between them, and whatever you decide, you must not
normalise the characters themselves: no quote folding, no ligature expansion, no
whitespace collapsing inside an item, no `normalize()`.

Be honest in your report about what "character-identical to its text layer" can mean
given that the parser gives you items rather than a string. Line breaks are inserted by
your assembly, not present in the source, so state the rule you used and the test that
proves it. Do not claim a fidelity you did not achieve.

**3. A typed rejection, never empty text.** A PDF with no text layer produces a typed
rejection carrying a machine-readable reason, through the discriminated union ticket 02
set up. Never a success result with an empty string, which would let a clean verdict be
rendered over nothing.

Distinguish the reasons you can actually distinguish. "No text layer at all" and "a
scanned document" are not the same signal: a scan usually has no text layer, but a
scan that has been through OCR elsewhere has one full of misread text, and a
text-layer PDF with one image page is neither. Decide what you can detect from the
parsed output, give each detectable case its own reason code, and say in your report
which cases you cannot tell apart and what happens to them. A reason code that claims
more certainty than the detection gives it is worse than a general one.

Page-level image detection and a text-to-page ratio are the honest signals available
to you. Use them rather than guessing from the file name or the metadata.

**4. Completeness comes out the same way as for pasted text.** PDF input produces a
completeness reading through the same code path ticket 02 built. Do not write a second
completeness assessor for PDFs. If the structural signals need a PDF-specific input,
pass it in; do not fork the module.

## Tests, `tests/pdf-extraction.test.ts`

Deterministic, no network. You need PDF fixtures and none exist, so you will create
them under `tests/fixtures/pdf/`. Build them programmatically if you can do it without
a new dependency, or hand-craft minimal valid PDFs as byte strings, which is entirely
doable for the cases you need and makes the test self-explanatory. Say in your report
how you made them.

Fixtures you need: a PDF with a real text layer whose exact expected text you know, a
PDF with no text layer at all, and a PDF whose pages are images. If you can only build
some of them honestly, build those and say which you could not and why, rather than
faking a fixture.

- A text-layer PDF yields the expected text, asserted character for character against
  a known string.
- A PDF with no text layer produces a typed rejection with a machine-readable reason,
  and the result is not a success with empty text. Assert on the discriminant.
- A PDF whose pages are images produces a refusal with its own reason.
- The reason code is machine-readable: assert on the code, not on the message, and
  assert separately that a reader-facing message exists for every reason code your
  union declares, so a new code cannot ship without copy.
- PDF input produces a completeness reading, through the same assessor pasted text
  uses.
- Pasted-text extraction still behaves exactly as ticket 02's tests assert. Run the
  existing suite and do not weaken any of its assertions.
- No network call during the run.

## The screen

Upload sits alongside paste, not instead of it. Pasting is the primary path, because
`ADR 0006` records that terms of service are web pages and subscription terms arrive
in email; the PDF covers the offer letter.

`DESIGN.md` has no file-input component and records that error and disabled states are
"not in the build. Do not invent one; the app shell will need them designed." So you
are designing one, and it has to stay in world: zero radius, a 2px ink keyline, black
on ink, the label register for its label, the global focus ring, no icon font, inline
SVG only if you need a mark at all.

A native file input styled to match is better than a bespoke drop zone here, because it
works with a keyboard and a screen reader without you rebuilding what the browser
already gives you. If you add a drop zone, the file input stays and stays reachable.

The refusal is a designed state and product copy, not error chrome. `DESIGN.md` gives
refusals a bar: an ink-colour bar in front of the line. Reuse that at the Operate
register's scale. No red, no warning triangle, no alert styling. The reader did nothing
wrong; their document is a photograph and Redline will not guess at photographs.

Operate register: motion 150 to 250ms, state only. WCAG 2.2 AA: the file input has a
real label, the refusal is announced when it appears, and the reason is conveyed in
text rather than by colour or an icon.

## Copy

Every reader-facing string through the `humanizer` skill: the upload label, the
refusal for each reason code, and whatever appears while a PDF is parsing.

The refusal copy is the most important writing in this ticket. ADR 0006 says it is part
of the product. It has to say what happened, why Redline will not proceed, and what the
reader can do instead, which is to paste the text if they have it. It does not apologise
at length, does not call itself an error, and does not blame the reader. It also should
not promise OCR later, because OCR is excluded on purpose and saying "not yet supported"
implies a roadmap that does not exist.

`CONTEXT.md` is binding: document, not file or upload, in reader-facing copy.

Say in your report that you ran the skill.
