## What to build

The fourth seam, at `src/qa/`. In: extracted text and a question. Out: a grounded
answer with its source sentence, or a refusal.

The reader asks a question about the document in their own words and pursues what
worries them rather than what was flagged.

## The two things that matter

**1. The answer's source sentence runs through the same verification code as a
flag's.** Import `src/analysis/verify.ts`. Do not copy it, do not write a second
version, do not relax it for answers. An answer whose source sentence does not appear
verbatim in the extracted text is not shown. Verification is code, not prompting, so
that it cannot degrade when the model or the prompt changes.

If reusing the analysis seam's verifier from the question seam feels like the wrong
dependency direction, move the verifier somewhere both seams import from, rather than
duplicating it. Say what you did in your report. Duplication here is the failure mode:
two verifiers drift, and the one on the answer path is the one nobody watches.

**2. A question the document cannot answer is refused, not guessed at.** The refusal
says the document does not address it. It does not answer from general knowledge, it
does not answer partially, it does not offer what the document probably means, and it
does not suggest what similar contracts usually say. `tests/fixtures/questions.json`
holds ungrounded questions chosen to be hard rather than silly: they sound answerable
and are not. "Is this arbitration clause enforceable in California" is the shape,
because enforceability is never in the document.

Ask the model for a refusal as a typed outcome rather than as prose you then have to
classify. A structured response where the model says whether it can ground an answer,
validated with `zod`, and where an ungrounded response carries no answer field at all,
is much harder to get wrong than parsing "I cannot find" out of a sentence. Then
enforce it in code: an outcome claiming to be grounded whose span does not verify
becomes a refusal, because the code's judgement beats the model's claim.

No answer draws on anything outside the document. There is no external fact base on
this path, unlike a flag, and you should not add one.

## How to do it

The model call is server-side only, in a route handler at `app/api/ask/route.ts`. The
model client is injected, exactly as at the analysis seam, and the deterministic suite
uses the stub. Extend `src/model/stub.ts` so it can serve question payloads built from
`tests/fixtures/questions.json`, including a payload that claims to be grounded while
returning a span that is not in the document, because one of your tests needs that.

The model id comes from `process.env.OPENROUTER_MODEL` and appears nowhere in source.

## Tests, `tests/qa.test.ts`

Deterministic, stub only, no network, no key.

- Every grounded question in the fixture returns an answer and a source sentence, and
  each source sentence appears verbatim in the extracted text. Loop over the fixture's
  grounded list rather than picking one.
- Every ungrounded question in the fixture returns a refusal. Loop over the whole
  list. Proposed 100% refusal, so the test asserts every one and not a proportion.
- A stubbed model claiming a grounded answer with an unverifiable span produces a
  refusal, not an answer. This is the test that proves code beats the model's claim.
- A span differing from the document by one curly quote or one space produces a
  refusal. The same strictness as a flag, proved separately here so a future relaxation
  on this path is caught.
- The refusal is a typed outcome distinguishable from an error and from an empty
  answer. A consumer must be able to tell "the document does not address this" from
  "something went wrong" without matching on copy.
- No network call during the deterministic run: fail the test if `fetch` is called.
- An empty question, and a question that is only whitespace, do not reach the model.
  Decide the behaviour and test it.

## The screen

The question box is anchored where the document ends, not floating over it. That is
from the app-shell brief and it is deliberate: a panel over the document hides the
thing the reader is checking against.

`DESIGN.md` gives you the components. Each question gets the 2.75rem by 0.5rem ink tab
above it, which is the tab-bar motif. A cited answer's source sentence sits in a
cool-grey blockquote with a 0.5rem ink underline beneath it. The field is the paste
field's sibling: white, 2px ink keyline, zero radius, cyan caret, a 3px cyan outline
on focus at zero offset with the field's own edge not moving, and a visible label
above it in the label register.

`DESIGN.md` records that the question box in the shipped landing page reads closer to
documentation than to the world the fold establishes, and names that as a defect the
build carries rather than a rule. Follow the fold's register, not that section.

A refusal is a designed state, not error chrome. `DESIGN.md` gives refusals a bar:
in the landing page's refusals list each one carries a `clamp(2.5rem, 6vw, 5.5rem)` by
1.25rem ink-colour bar in front of it. Reuse that device at the Operate register's
scale. Do not use red, do not use a warning triangle, do not use an icon font, and do
not style it as an error. The reader asked a fair question and the document is silent;
that is information, not a fault.

Operate register throughout: motion 150 to 250ms and state only, no load-time snap.

WCAG 2.2 AA. The answer region announces itself when it arrives. The relationship
between an answer and its source sentence is a real accessible relationship, not
proximity. A screen reader user must be able to tell an answer from a refusal
immediately.

## Copy

Every reader-facing string through the `humanizer` skill: the field's label, its
placeholder, the button, the answer's framing, the source sentence's label, the state
while the answer loads, and above all the refusal.

The refusal is the hardest string in this ticket and worth real attention. It says the
document does not address the question. It does not apologise, does not blame the
reader for asking, does not hint at what the answer might be, and does not suggest
they ask a lawyer, which would be advice. `CONTEXT.md` is binding: document, reader,
source sentence.

Say in your report that you ran the skill.

## Criteria, restated

- [ ] The reader can ask a free-text question about the analysed document.
- [ ] An answerable question returns an answer plus its source sentence, quoted verbatim.
- [ ] The answer's source sentence is verified against the stored text by the same code path a flag uses; an unverifiable answer is not shown.
- [ ] A question the document cannot answer is refused, and the refusal says the document does not address it.
- [ ] No answer draws on anything outside the document.
- [ ] Both the answer path and the refusal path are covered by deterministic tests with a stubbed client.
