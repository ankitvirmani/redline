## What already exists

A Next.js 15 App Router application at the repository root, TypeScript, React 19.
`app/globals.css` carries the token block copied from `landing/styles.css`. The
landing page is ported to `app/landing/page.tsx` and is temporarily served at
`/landing`; ticket 14 moves it to the root. `app/page.tsx` is yours.

Two fixture documents and their sidecars are under `tests/fixtures/`.

No test runner is wired. That is part of this ticket.

## What to build

A reader opens the app at `/`, pastes a document into a box, submits, and sees
exactly what they pasted rendered back, character for character, with a count.
Nothing is analysed. Nothing is stored, in a database, in `localStorage`, in a
cookie, or on the server.

Round-trip fidelity is the real work. The page is the lesser half.

## How to do it

**Wire Vitest.** Add `vitest` as a dev dependency and nothing else. Add
`"test": "vitest run"` to `package.json` scripts, alongside the `typecheck`,
`build` and `dev` scripts already there. `npm test` must run the whole suite once
and exit, never watch. Configure it so a `.test.ts` file anywhere under `tests/`
and `src/` is picked up, TypeScript and ESM work without a build step, and the
suite makes no network call. Put the config in `vitest.config.ts`.

**Put the fidelity logic in a function, not in the component.** Create
`src/domain/text.ts` exporting the function that counts characters and whatever
else the page needs. The test tests that function and the submit path, not the
rendered pixels. A count of characters means Unicode code points, not UTF-16 code
units: decide which you report, say so in your report, and make the test prove the
choice on text containing an astral character. A ligature glyph and an emoji count
differently under the two, and a reader looking at a count wants the number of
characters they can see.

**Render the pasted text back losslessly.** No trimming, no whitespace collapsing,
no smart-quote or ligature normalisation, no line-ending rewriting, no
`dangerouslySetInnerHTML`. Newlines and runs of spaces must survive to the screen,
which is a CSS decision (`white-space: pre-wrap`) as well as a data one. The
project's whole citation mechanism rests on this text being untouched.

**Tests.** At minimum:

- Round-trip fidelity over text containing curly quotes, a ligature glyph,
  a non-breaking space, a tab, a run of double spaces, trailing whitespace on a
  line, and an astral character. Assert character-for-character equality, not a
  normalised comparison.
- Round-trip fidelity over the whole of `tests/fixtures/adhesion-contract.txt`,
  read from disk. It contains every awkward character on purpose.
- The character count is correct for a string containing an astral character.

Write the tests as `tests/text-fidelity.test.ts`. They set the convention every
later ticket follows, so make them assert what a reader would observe rather than
internal shapes.

**Delete `vercel.json`.** The ticket explains why: it sets `framework` to null and
`outputDirectory` to `landing`, which blocks Vercel from detecting Next.js. Deleting
it is the whole fix. Do not replace it.

**The screen.** One page. It obeys `DESIGN.md`: zero radius, a 2px ink keyline on
the textarea, cyan primary button with black uppercase label and the arrow pushed to
the far edge, the visible label above the field in the label register, the global
focus ring, Archivo from the tokens. The pasted text renders in the Document
register: 400 weight, 0.9375rem, 1.72 line-height, justified and hyphenated above
520px, held at a 26rem measure. Left-aligned and unhyphenated below 520px. This is
the Operate register from the app-shell brief, not the landing page's display
register: no scattered fragments, no overprint bar, no load-time snap, no display
type above 2.875rem. Motion is 150 to 250ms and conveys state only.

The character count sits alongside the text, in the label register.

WCAG 2.2 AA. The textarea has a real visible label bound to it. Focus order runs
label, field, submit, result. The result region announces itself when it appears.

**Copy.** Every string a reader sees goes through the `humanizer` skill before you
finish: the label, the placeholder, the button, the count, the empty state, and
whatever you show when someone submits nothing. Use `CONTEXT.md` vocabulary:
reader, document. Not user, not file, not upload. Say in your report that you ran
the skill.

## Criteria, restated so you can check yourself

- [ ] The app runs locally with one page at `/` holding a paste box and a submit action.
- [ ] Submitting renders the pasted text back character for character, including whitespace, smart quotes, ligatures and line breaks.
- [ ] A character count is shown alongside the text.
- [ ] `npm test` runs the suite in one command and exits.
- [ ] At least one test asserts round-trip fidelity of text containing smart quotes, ligatures and irregular whitespace.
- [ ] No document text is persisted anywhere. No database, no `localStorage`, no `sessionStorage`, no cookie, no server write, no log line containing document text.
- [ ] `vercel.json` is deleted.
