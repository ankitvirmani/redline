## The question the ticket says to stop and ask is already answered

The ticket says to stop and ask which model before writing code. The owner is not
present and supplied the answer with the run instruction:

**The model is whatever `OPENROUTER_MODEL` says.** It is read from that one
environment variable at every call site and never written into source, a test, a
comment, a default, or a fallback. Both `OPENROUTER_MODEL` and `OPENROUTER_API_KEY`
already exist in `.env.local`, which is gitignored.

The request shape is fixed, not yours to choose:

```
POST https://openrouter.ai/api/v1/chat/completions
Authorization: Bearer ${process.env.OPENROUTER_API_KEY}
{
  model: process.env.OPENROUTER_MODEL,
  provider: { order: ["fireworks"], allow_fallbacks: false, require_parameters: true },
  reasoning: { effort: "low" },
  response_format: { type: "json_schema", json_schema: { name, strict: true, schema } },
  messages: [...]
}
```

`allow_fallbacks: false` and `require_parameters: true` together mean OpenRouter will
fail the request rather than silently route to a provider that cannot honour the
structured-output parameters. That failure is the behaviour we want, so surface it as
a real error rather than retrying without the constraints.

**Never print, log, commit or echo either variable's value.** The GitHub repo is
public. If you find a key in committed source or in a file that is not gitignored,
stop, do not commit anything, and report it as the first line of your report.

## What to build

The first time a reader's document reaches a real model. Analysis and question
answering run against OpenRouter instead of the stub, and the product works end to end
on a real adhesion contract.

**1. Finish the real client.** `src/model/openrouter.ts` exists from ticket 04.
Make it correct and make it honest about failure. It needs: the exact request shape
above, a JSON schema per call type passed through `response_format`, `zod` validation
of what comes back before a single field is trusted, a timeout, and typed errors for
the cases that actually happen. Those cases are a missing key, a missing model
variable, a provider refusal under `allow_fallbacks: false`, a rate limit, a timeout,
a non-JSON body, and a body that parses but fails the schema. Each of those is a
different thing for the reader and for the owner debugging it, so do not collapse them
into one.

Do not retry automatically on a schema failure with a loosened schema. That would be
the silent degradation the product is built to avoid.

**2. Wire it into the route handlers.** `app/api/analyse/route.ts` and
`app/api/ask/route.ts` inject the real client; tests inject the stub. The key never
reaches the browser, so the client is only ever constructed server-side. Make that
structurally true rather than a convention: if the module can be imported into a client
component without an error, someone eventually will.

**3. `npm run smoke`.** A script at `scripts/smoke.ts`, wired to
`"smoke"` in `package.json`, that runs `tests/fixtures/adhesion-contract.txt` through
the real pipeline end to end and prints its flags with their source sentences. This is
the owner's acceptance check for the whole build, so make its output readable by a
person: for each flag, the rank, the clause type, the severity band, the confidence,
the consequence, and the source sentence quoted in full. Then the summary, the
completeness reading, and the count of flags dropped because their span did not verify.

It must go through the real seams, not reimplement them. The whole point is that it
exercises extraction, analysis, verification and ranking in the order the product does.

It must also ask the question box one grounded question and one ungrounded question
from `tests/fixtures/questions.json` and print both results, because the ticket's
criteria cover both paths.

When `OPENROUTER_API_KEY` is absent it must say so plainly and exit non-zero rather
than falling back to the stub. A smoke script that silently passes without a model
would be worthless as an acceptance check.

**4. Keep the deterministic suite clean.** `npm test` still passes, still uses the
stub, and still makes no network call. Assert it: the existing tests should already
fail if `fetch` is called, and if they do not, add that. Do not add a test that calls
the real model; the real-model measurement is ticket 13.

## Tests, `tests/openrouter-client.test.ts`

Deterministic. You are testing the client's own behaviour, which means testing what it
sends and how it handles what comes back, with `fetch` replaced at the boundary. That
is not mocking the thing under test: the thing under test is the client's request
construction and response handling, and the network is the boundary.

- The request body carries the model from `OPENROUTER_MODEL`, the pinned provider
  block exactly as specified, reasoning effort low, and a `json_schema` response
  format. Set the environment variable to a made-up value in the test and assert it
  appears in the body, which also proves it is read rather than hardcoded.
- A missing `OPENROUTER_MODEL` and a missing `OPENROUTER_API_KEY` each produce their
  own typed error before any request is attempted.
- A non-JSON body, a body that fails the schema, a 429 and a timeout each produce
  their own typed error.
- No model identifier string appears anywhere in committed source. Write this as a
  test that greps the source tree, because it is the criterion most likely to be broken
  by a later careless change and a test is the only thing that will catch it. Exclude
  `.env.local` and anything gitignored from the search, and make the test explain what
  it is protecting.
- The deterministic suite makes no network call.

## Running the real thing

After the deterministic suite passes, run `npm run smoke` once against the real model,
with the key from `.env.local`. Report:

- how many flags came back, and how many survived verification
- for each surviving flag, its clause type, severity band and source sentence
- how many flags were dropped for an unverifiable span, which is the number the owner
  most wants to see
- the summary it produced
- the grounded question's answer and its source sentence
- whether the ungrounded question was refused
- the completeness reading

Do not tune the prompt to make the output look better and then report the tuned run as
if it were the first. If you change the prompt after seeing results, say so and report
both runs.

If the run fails for a reason outside your control, a rate limit or a provider
refusal, report the exact error and do not work around it by relaxing
`allow_fallbacks` or dropping `require_parameters`. Those are pinned deliberately.
