## What to build

A reader submits a document and sees the clauses that could hurt them, each showing
the exact sentence it was drawn from, quoted verbatim, with a severity and a
confidence. Flags are unordered at this stage. Ordering is ticket 06 and you must
not do it: returning them in an order that looks right would hide whether ticket 06
works.

The seam lives at `src/analysis/`. In: extracted text. Out: a plain-English summary
placeholder field, the set of clause types checked, and the verified flags. The
summary's content is ticket 05; carry the field and leave its production to 05, or
produce it if it falls out of the same call, but do not build a screen for it.

## The three things that matter most

**1. Verification is code.** The model returns spans. Your code checks each span
against the stored extracted text. A span that does not appear verbatim means the
flag is dropped before the seam returns, and the drop is logged as a defect. Put
this in `src/analysis/verify.ts` as a pure function with no knowledge of models.

Verbatim means exact substring. No trimming before comparison, no whitespace
collapsing, no quote folding, no case folding, no Unicode normalisation. If a model
returns a span that differs from the document by one curly quote, that flag is
dropped. That is the correct behaviour and it is the point: a fabricated risk has no
matching sentence, so the check catches it before display rather than after someone
acts on it.

Do not repair a near-miss span. Do not fuzzy match. Do not search for the closest
sentence. A repaired span is a citation the reader cannot trust, and the repair
would be exactly the silent degradation ADR 0001 exists to prevent.

The verification must also return where in the text the span was found, because
ticket 08 and the change bar need to mark the sentence inside the rendered document.
An offset range is the honest way to carry that. If a span appears more than once in
the document, decide what to do and justify it in your report.

Log the defect through one function you write, so that later tickets and the eval
suite can count drops. Do not log the document text or the span itself to a place
that persists; the log is a defect counter, not a store of someone's contract.

**2. Severity is assigned here, from the instance's terms.** The clause type sets a
baseline band and the instance's own terms move it within or across bands. A
three-day cancellation window and a ninety-day one are the same type at different
severities. `tests/fixtures/adhesion-contract.json` plants exactly that pair on
purpose, with two different `expectedSeverityBand` values: use it to prove the
behaviour.

Bands are `critical`, `high`, `moderate`, and the baselines per type are in `PRD.md`
section 5. Put the seven types and their baselines in `src/domain/clause-types.ts`
as data, with the four regulator-evidenced types (arbitration and class-action
waiver, auto-renewal, fee escalators and late fees, non-compete) marked apart from
the other three (unilateral modification, limitation of liability,
indemnification), because ticket 13 reports recall separately for the two groups.

Severity has to be a property of the clause as written rather than a lookup on its
category. How you achieve that is yours to design: the model can be asked to report
the terms that set the band, and code can hold the baseline and the rules that move
it. Whatever you build, a test must prove that two instances of one type land in
different bands, and it must be the terms and not the type that did it.

**3. The model client is injected, and the model id comes from one variable.**
Write the interface at `src/model/client.ts`. Write the real OpenRouter
implementation at `src/model/openrouter.ts` following the request shape in the
standing brief exactly: the model from `process.env.OPENROUTER_MODEL`, the pinned
provider block, reasoning effort low, and `response_format` with a strict
`json_schema`. Ticket 10 is the one that runs it against a real model; build it
correctly now and do not call it from a test.

Write the stub at `src/model/stub.ts`. It builds its payloads from the fixture
sidecars, so the deterministic suite runs with no key and no network. It must also
be able to return, on demand, a payload whose span does not appear in the document,
because one of your tests needs that.

No model id in source, in a test, in a comment, or as a default value. The model
call happens server-side only, in a route handler at `app/api/analyse/route.ts`,
because the key must never reach the browser.

Validate the model's JSON with `zod` before a single field is trusted. A response
that fails the schema is a defect, not something to patch up field by field.

## Tests, `tests/analysis.test.ts`

All deterministic, stub only, no network, no key.

- Every flag the seam returns has a source sentence that appears verbatim in the
  extracted text. Assert this programmatically over every flag of every fixture,
  not on a sample. Write it as a loop over the fixtures directory so a fixture added
  later is covered automatically.
- A stubbed model returning an unmatchable span produces zero flags and a logged
  defect. Assert both halves.
- A stubbed model returning a mix of matchable and unmatchable spans returns only
  the matchable ones, with the right count.
- A span differing from the document by one character, one curly quote, or one
  space is dropped. Three separate cases. This is the test that proves nothing
  fuzzy-matches.
- Severity responds to the instance's terms: the two planted cancellation windows
  land in the bands the sidecar expects, and they differ from each other.
- All seven clause types can be represented, proved by a flag of each type passing
  through the seam intact rather than by asserting a constant has seven entries.
- The suite makes no network call. Assert it rather than assuming: fail the test if
  `fetch` is called during the deterministic run.

## The screen

Flags render in the reading field with the document. This is the Change Bar, the
signature device in `DESIGN.md`, and it is the one thing on this surface that is
not negotiable stylistically, because it is the product's rule made visible. A
source sentence in the document carries three marks at once: a 0.5rem
full-saturation underline in the flag's own ink, the left-edge ink tab drawn by the
single permitted zero-blur box-shadow, and the code chip appended inline. All three
use `box-decoration-break: clone` so every wrapped line fragment gets them
independently. At rest the underline drops to a 34 to 40% mix into white and the tab
goes transparent, both over 220ms. Selection works in both directions: a flag opens
its sentence, and the sentence opens its flag and moves focus to it.

Read the landing page's implementation at `landing/styles.css` and
`app/landing.css` for how this is built, and reuse it rather than reinventing it.

The Identity-Not-Severity Rule is absolute and it is also the WCAG commitment:
colour tells one flag from another and never encodes how bad it is. Severity is
carried by the word, "Critical", "High", "Moderate", and by list order. Confidence
is a separate signal on the flag and must not look like severity. Audit your own
work the way `DESIGN.md` says to: recolour every bar at random, and if the ranking
survives, the rule holds.

This is the Operate register. No scattered fragments, no overprint bar, no display
type above 2.875rem, no load-time snap. Motion 150 to 250ms, state only.

Flags are unordered here, so render them in the order the seam returns them and do
not sort. Ticket 06 adds the order.

WCAG 2.2 AA. A source sentence is verbatim legal prose read under pressure: focus
order, screen-reader handling of a long quoted passage, and the relationship between
a flag and its sentence all have to work without sight. Bind them with real
accessible names and relationships, not with colour and position.

## Copy

Every string a reader sees goes through the `humanizer` skill before you finish:
severity words, confidence wording, the flag's heading, whatever you write around
the source sentence, and the state shown while analysis runs. `CONTEXT.md` governs:
flag, source sentence, severity, confidence. Not issue, finding, alert, citation,
excerpt, priority or risk level. Say in your report that you ran the skill.

## Out of bounds

No ranking and no sorting: ticket 06. No two-tier consequence, no external context
fact base, no document-granted exit rendering: ticket 08 (carry the fields in the
types if the model call produces them, but do not build the fact base or the render).
No question box: ticket 09. No real model call from a test or from the smoke path:
ticket 10. No auth, no storage, no library, no red lines. No jurisdiction-neutrality
copy: ticket 08 places it.

Do not touch `app/landing/page.tsx`, `landing/`, `tests/fixtures/` (read them, do
not edit them), `docs/`, `PRD.md`, `PRODUCT.md`, `DESIGN.md`, `CONTEXT.md`, or
anything under `.scratch/`. Do not commit.
