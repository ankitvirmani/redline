## What to build

`src/ranking/`. In: flags and red lines. Out: ordered flags, red-line marks, and
the clean-document determination. It contains no model call, no network call and no
database access, and that is what makes ordering deterministic and cheap to assert.

This ticket does the ordering. Red-line marks are ticket 12 and the clean-document
determination is ticket 07, both of which land in this same seam. Design the seam so
those two fit without being rewritten: take red lines as a parameter now and accept
an empty list, and return a shape that has room for a clean-document determination.
Do not implement either behaviour.

## Order by leverage lost

Leverage is what a reader would otherwise be able to do: sue, leave, or refuse a
change. Its loss is what makes a clause dangerous rather than merely unusual.

Ranking consumes severity, it does not compute it. Severity was assigned during
analysis because it is a property of the clause as written. So the primary key is the
severity band, and within a band the tie breaks on leverage lost.

That means leverage lost has to be something ranking can read off a flag. Decide
where it comes from and justify it in your report. Two honest options: it is a
property of the clause type, held as data in `src/domain/`, which is defensible
because the ability a clause removes is a fact about the kind of clause; or analysis
reports it per instance. Pick one, and if you pick the first, put it next to the
clause-type baselines rather than in the ranking module, because it is domain
knowledge and not ordering logic.

**Ubiquity is not safety.** An arbitration clause is in nearly every consumer
contract and ranks first here. A ranking driven by how unusual a clause is would bury
it and surface harmless oddities instead, which is precisely why this product does
not use one. Nothing in your implementation may read a frequency, a rarity, a
market-norm figure, or a novelty signal.

**Confidence does not move the order.** How sure we are that a clause is what we
think it is, is a different question from how much it costs. Confidence is carried on
the flag and rendered separately. A test must prove that reordering by confidence
changes nothing.

**The order is total and stable.** Two flags that tie on band and on leverage lost
must still come out in a fixed order across runs, or the tests will flake and the
reader will see the list move between analyses of the same document. Decide the final
tiebreaker, say what it is, and make it something a reader would not find arbitrary.
Do not use the model's output order, which is not stable.

## Tests, `tests/ranking.test.ts`

Pure-function tests over fixed flag sets built in the test file. No fixtures needed
for most of them, no model, no network, no database.

- A document containing both an arbitration clause and a merely unusual clause puts
  arbitration higher. Build both flags by hand so the test reads as the claim it is
  making.
- Ties break on leverage lost: two flags in the same band where the one removing
  more leverage comes first.
- Confidence does not affect order: take a ranked list, rewrite every confidence
  value to an adversarial arrangement, rank again, and assert the order is identical.
- The order is total and stable: rank the same set twice, and rank a shuffled copy of
  the same set, and get the same order all three times.
- Ranking is pure: the same input returns the same output and the input is not
  mutated. Assert the input array and its flag objects are unchanged after the call.
- No network and no database: fail the test if `fetch` is called during the run.
- Every flag that went in comes out. Ranking never drops one. This matters because
  tickets 07 and 12 land here and a future change that filters would be a serious
  regression.
- The seam accepts an empty red-line list and behaves identically to being given
  none.

## The screen

The reader sees flags in ranked order. That is the only screen change: replace the
seam-order rendering ticket 04 left with the ranked order. Do not redesign the flag,
do not restyle it, do not add a severity colour. `DESIGN.md`'s Identity-Not-Severity
Rule means the order itself is one of the two things carrying severity, alongside the
word, so the visible order is load-bearing rather than cosmetic.

Give each flag its rank where the reader can see it, using the rank badge
`DESIGN.md` records: ink field, tabular numerals, zero radius. Check `landing/` for
how the shipped page renders it.
